# Milestone 6: Proof Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Prove sub-project 1 against the spec's "done" table in both target browsers. Chrome is proved by the e2e suites. Safari is proved by a report run that posts timings, the world's fingerprint and screenshots back to the dev server.

**Architecture:**
- A check mode of the game page (`?check=<run>`) loads normally, then measures and photographs the six standard views. It posts a JSON report and PNGs to a dev-server endpoint, which writes them under `artifacts/<run>/`.
- Chrome runs the check in the e2e suite.
- `npm run safari` opens the same URL in Safari with `open -a Safari`, waits for the report, and judges it.

**Tech Stack:** TypeScript, Vite 8 dev-server middleware, Playwright (Chrome), macOS `open`, Safari 26.6.

**Spec:** docs/superpowers/specs/2026-10-21-trenchline-web-world-design.md ("What done means", Testing → Safari report run, Build order step 6).

## Global Constraints

- From navigation to "click to play": ≤ 4 s in Chrome and ≤ 8 s in Safari 26, on the M1 Pro from a local server.
- GPU frame ≤ 14 ms on the M1 Pro in both browsers, for each standard view at the high preset's 1.5 MP with dynamic resolution off.
- The same seed gives the same world bytes in Chrome and in Safari: the fingerprint equals the golden `dea2a4cd…d67c`.
- The Python reference passes its own suite.
- Opening Safari is the only effect outside the repo. Nothing is pushed.
- Commits end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

- **Safari without timestamp queries.** GPU time must still be measured, from `queue.onSubmittedWorkDone()` latency, and the report must say which measure it used. Pinned in Task 1, which reports `timer: 'timestamps' | 'submitted-work'`.
- **A check that never reports.** A page error, or WebGPU failing in Safari, must still post a report carrying the error rather than leave the runner waiting forever. The runner times out after 4 minutes with a clear message. Pinned in Tasks 1 and 2.
- **Screenshots from a WebGPU canvas.** They are read in the frame that drew them; a blank PNG counts as a failure, not a pass. Pinned in Task 1 (the PNG's luminance spread is checked).

### Task 1: The check page, its report endpoint, and Chrome's run

**Files:**
- Create: `src/app/check.ts`, `tools/vite-plugin-report.ts`, `tests/fixtures/golden.json`, `tests/e2e/check.spec.ts`
- Modify: `src/app/main.ts` (start the check when `?check=` is present), `vite.config.ts` (register the plugin for `serve`), `tests/world/generation/world.test.ts` (read the golden from the fixture)

**Interfaces:**
- **Endpoints.**
  - `POST /__report/<run>/report.json` (a JSON body) and `POST /__report/<run>/<view>.png` (PNG bytes) write `artifacts/<run>/…`.
  - `<run>` and the file name must match `/^[a-z0-9-]+$/`. Anything else gets 400, so the endpoint cannot write outside `artifacts/`.
- **The report:**
  ```
  { run, userAgent, timer: 'timestamps' | 'submitted-work', promptMs, timings, fingerprint, golden: boolean,
    views: [{ name, time, gpuMs, res: [w, h], shot: '<name>-<dusk|night>.png', spread }], errors: string[] }
  ```
- **Hooks.** `checkDone` (a promise) and `checkReport`, for the e2e spec.

- [ ] **Step 1: Write the failing tests.**
  - `tests/e2e/check.spec.ts`, `'the check reports the world, its timings and every view'`:
    - Open `/?check=chrome-e2e`, and await `__trenchline.checkDone`.
    - `artifacts/chrome-e2e/report.json` exists. Its `golden` is true, and `errors` is empty.
    - There are six views. Each has `gpuMs` > 0, `res` at 1.5 MP, and a PNG on disk whose `spread` is > 4/255.
    - `timer` is `timestamps`.
  - `world.test.ts` reads `tests/fixtures/golden.json`, which holds `{ seed: 7, fingerprint }`.
- [ ] **Step 2: Run.** `npx playwright test tests/e2e/check.spec.ts`. Expected: FAIL, because no check runs.
- [ ] **Step 3: Implement.**
  - The check sets `setQuality({ preset: 'high', dynres: false })`.
  - For each view, at its own time of day and then the other, it waits `waitConverged()` and then 30 more frames:
    - With timestamps, `gpuMs` is `stats().gpuMs`.
    - Without them, it is the median of 30 latencies from `queue.submit` to `onSubmittedWorkDone`.
  - Each shot is captured from the canvas in the frame that drew it (`toBlob`, at its full size); `spread` is measured on a 160 × 100 copy.
  - Failures, including a GpuUnavailable or a lost device, still post a report with `errors` filled.
- [ ] **Step 4: Run.** The check spec passes, and `npm test` stays green.
- [ ] **Step 5: Commit** "Check the world in any browser: timings, the fingerprint and the six views, reported to the dev server".

### Task 2: Safari's run

**Files:**
- Create: `tools/safari-report.mjs`
- Modify: `package.json` (add `"safari": "node tools/safari-report.mjs"`)

- [ ] **Step 1: Implement** the runner. It:
  1. starts the dev server on port 5340;
  2. deletes `artifacts/safari/`;
  3. runs `open -a Safari http://localhost:5340/?check=safari`;
  4. polls for `artifacts/safari/report.json` for up to 4 minutes;
  5. prints a table: prompt ms against 8000; the fingerprint against the golden; each view's GPU ms against 14, with the timer used; the errors;
  6. exits 1 on any failure, and on a timeout says "Safari never reported: is WebGPU enabled (Safari 26+)?".
- [ ] **Step 2: Run** `npm run safari`. Expected: the report arrives and every criterion passes.
  - A failure here is a finding. Fix it with a failing test in the module concerned, where one can be written in Chrome or Node. Ledger the measurement before and after.
- [ ] **Step 3: Review the Safari PNGs by eye** against Chrome's (`artifacts/chrome-e2e/`). Check the look, the fog, night, and that the far field matches.
- [ ] **Step 4: Commit** "Run the check in Safari and judge its report".
